## 0 · 动因实录（2026-11-18 夜，真实事故）

NAS 执行 Python 桥全舰队禁令时，向 **笔记本 指挥部** bot 发路条回执任务 `FNB-DEPR-01`：

- 发送侧：API `code:0`、`message_id=om_x100b60eefcc1a0a…` —— 飞书确认"消息已送达服务器" ✅
- 接收侧：**永无回执** —— 指挥部电脑关机 / 桥进程离线 ❌
- 结论：**飞书消息是 fire-and-forget**。API 成功 ≠ 对方 bot 进程收到 ≠ 会被执行。任务丢失完全静默，发送方无从得知。

这正命中"架构优化点"第 4 条的原话：**"派活前先查在线，避免任务发给离线设备（飞书消息发出去收不回）"**——今晚实测复现，优先级应提档。

## 1 · 提案：MQTT 风格 Presence 协议

借用 MQTT 的三个核心语义（不需要真上 MQTT，见 §3 载体）：

| MQTT 概念 | 舰队语义 | 行为 |
|---|---|---|
| **Retained 状态消息** | `fleet/<device>/status` | 桥上线即发布 `online`（含版本/chat_id/时间戳），状态可被随时读取 |
| **LWT 遗嘱 + keepalive 超时** | **离线不是宣布出来的，是超时判出来的** | 桥崩溃/断电不来得及道别——presence 靠 TTL 兜底（如 90s 无心跳即判 offline），桥正常退出时主动发 `offline` 加速收敛 |
| **Subscribe before publish** | fleet_send/路条派活前置检查 | 发送前先查接收方 presence：**在线 → 发**；**离线 → 立即向发起方回"接收方离线（last_seen=…）"**，不再静默等死 |

再加一层 **ACK 往返**（路条消息要求接收方先回 `ACK <taskId>` 再干活，发送方超时则升级处理——群里 @ 人报备）。"发了没人回"从黑盒变成**可测的失败**。

可选进阶：**store-and-forward**——离线设备的任务入队，等它上线自动投递（MQTT 持久会话的同款思想）。

## 2 · 验收标准（实现后照此测试）

1. 对**在线**设备派活 → 正常执行（不回归）
2. 对**关机**设备派活 → 发起方 **≤10 秒**收到"接收方离线（last_seen=xxx）"，永不静默
3. 设备恢复上线 → presence 翻回 online；若做了队列，积压任务自动投递
4. 桥被 kill -9 / 拔电 → TTL 超时后被正确判离线（LWT 语义的关键用例）

## 3 · 载体选型（不新增服务器为前提）

| 候选 | 优点 | 代价/风险 |
|---|---|---|
| **lark-base 多维表格行**（心跳表，即"架构优化点#2"同一张表：设备/last_seen/版本/状态） | 零新增服务；宏万可视化；API 现成 | 心跳写入频率（90s/台≈可忽略）；依赖飞书 API 可用性 |
| git 仓库 state 文件 | 零新基建，全设备天然共享 | 多机并发 push 锁竞争；秒级延迟；污染提交历史 ⚠️ 不适合高频心跳 |
| ~~真 MQTT broker（mosquitto 常驻NAS）~~ **已否决（宏万 2026-11-18 夜）** | presence/LWT/QoS/retain 全套原生，语义最正 | **否决理由（硬约束）**：broker 要求"所有设备都能主动连进来"，而NAS **无公网 IP、无固定 IP**；唯一补救（Tailscale/ZeroTier 类虚拟组网）宏万国内实测效果差、明确不考虑 → 路线不成立。剩余场景仅"纯家庭内网闭环实验"，不进路线图主线。另：多一个常驻服务与一条网络依赖，开源用户多一步安装 |
| 飞书群消息卡片 | 无需新载体 | 无结构化订阅/查询，"查在线"能力弱 |

**载体拍板（宏万 2026-11-18 夜，全舰队适用）**：lark-base 心跳表 = **唯一主线**——每台桥 60s 写 `last_seen`（设备/last_seen/版本/当前任务），**90s TTL 超时判离线**（离线不由设备自己宣布），`fleet_send` 发送前查表（离线 → ≤10s 回发起方"接收方离线（last_seen=…）"），接收方先 `ACK <任务ID>` 再干活。**mosquitto / 真 MQTT 不再作为演进目标**（否决理由见上表 + §3.1）；若将来外部用户确实拿不到多维表格权限，另案重评，不挂在当前路线图上。

### 3.1 · 可达性约束（为什么载体必须是"所有设备出站可达"的东西）

- **舰队当前零入站**：收事件走 lark-cli 长连接（出站 websocket）、发消息走开放平台 API（出站 HTTPS）——所以设备在 NAT 后、没公网 IP 照样在线（`docs/PRINCIPLES.md:11`：「长连接事件推送（免公网 IP，NAT 后可用）」）。
- **推论**：任何要求"别的设备连进来"的载体（自建 broker、自建 HTTP 回调）等价于给每台设备提"公网 IP / 端口映射 / 虚拟组网"的要求，**在本舰队不成立**。心跳载体必须是天然的**出站可达公共中转**——飞书开放平台就是现成的那个。
- **NAS 的正确角色 = 出站值班员，不是被连的服务器**。它的价值在于 24h 不关机，因此承担只有常驻者干得了、且**全部主动出站**的活：① 扫心跳表，发现某设备 `last_seen` 复活就把它的积压任务补投（store-and-forward 的投递端）；② 掉线超阈值巡检 + 群里 @ 报备；③ 任务台账对账。
- **虚拟组网已排除**：Tailscale/ZeroTier 类，宏万国内实测体验差、明确不考虑。**后续任何提案不要再拿它当"NAS 跑 broker"的补救手段**。
