# 飞书消息发送强制规范（agent 间协作）

> **适用范围**：任何用 `lark-cli` / fleet 插件 / 桥接在飞书群里发消息的 agent（含 办公机、客户服务器、NAS）。
> **性质**：硬规矩，违反即视为发消息失败（不管 API 返回 ok）。
> 立规依据：2026-11-20 全天实测（4 次失败逐条定位）。

---

## 一、身份：只用 bot，禁止 user

| 场景 | 用哪个身份 | 为什么 |
|---|---|---|
| **agent → agent**（派活、回执、续派） | **bot 身份**（各设备自己的 bot）| 群里能看出是谁发的；不冒名任何人 |
| **人 → agent**（真人自己在群里 @bot）| 真人自己发，不需要 agent 代发 | — |
| **agent 替人转达** | ❌ **禁止** | 等于冒名本人发言 |

**禁止事项（硬性）**：
1. ❌ agent 用 `--as user` 发任何消息 —— **这是冒名宏万本人**，即使只是转述任务。
2. ❌ 群消息里不得出现发送人是真人用户名的 agent 消息。

**为什么必须这样**：agent 用 user 身份发出的消息，在群里显示为「杨宏万」，**收件人无法分辨是 agent 还是本人**，派活链路的责任链就断了；今天就发生过"agent 续派的消息署名显示成别人"的误判。

**附带好处（实测）**：bot 身份**没有 user 身份的 key-storage 锁** —— 同机并发时 user 身份会撞锁失败，bot 不会。

---

## 二、@：必须是结构化 at 标签，禁止字面量

**正确写法（text 消息）**：
```
<at user_id="ou_xxxxxxxxxxxx"></at> 正文……
```
其中 `ou_xxx` 是**被 @ 对象在该应用下的 open_id**。

**post 富文本**：
```json
{"tag":"at","user_id":"ou_xxx"}
```

**严禁**（这些是**错的**，哪怕 API 返回 ok）：
- ❌ 正文里写 `@某某`、`@_user_1`、`@_user_2` —— 这是**字面量**，不是 @
- ❌ 手打 `@小鲸鱼-客户服务器` 之类的显示名
- ❌ 用 `mention_name` 之类未经验证的字段名去碰运气

**为什么**：手写显示名或占位符，**飞书不会建立 mentions 关系** → 被 @ 的机器人**收不到事件**、群里也不显示高亮。表现为"消息发出去了但对方毫无反应"。

## 三、发完必须回读校验（三条，缺一不可）

```powershell
# 1) 取回刚发的消息
lark-cli im +messages-mget --message-ids <message_id> --as bot

# 2) 检查 mentions 非空且 id 正确
#    mentions: 小鲸鱼-客户服务器(ou_xxx) key=@_user_1     ← 合格
#    mentions: (空)                                        ← 不合格，重发

# 3) 检查 sender 是本机 bot（不是别家 bot，也不是 user）
#    sender: 小鲸鱼-办公机 / app (app=cli_xxx)               ← 合格
#    sender: 杨宏万 / user                                  ← 说明误用了 user 身份
```

**判定**：mentions 里必须有**被 @ 对象的 open_id**；sender 必须是 **bot 身份**。
**任一不符 → 当作没发出去，重发**（不要"先发了再说"）。

---

## 四、路条（任务路由）

所有 agent→agent 的任务消息，正文首行必须带：
```
[任务ID|发起方|派发深度N]
```
- 任务ID：全局唯一（如 `DEP-20261120-S1`）
- 发起方：发起 agent 的设备名（如 `办公机`）
- 派发深度：从 1 起，每转手 +1，**≤3**

**接收方收到无路条的消息 → 拒绝处理并回「格式无效」**（防止 agent 互相 @ 刷屏）。

## 五、身份互认表（各设备）

**同一个 bot 有两个 `ou_` id —— 取决于"谁在看"**：

`ou_` 是**应用内作用域**的 open_id：同一个 bot，在不同应用的视角下是**不同的 id**。

| 用途 | 该用哪个 id |
|---|---|
| 配置 `bot_open_id`（判断"是否 @ 我"）| **本方应用视角**（你自己应用里看到的那个）|
| @ 别人（`mention_open_id`）| **对方应用视角**（从群消息 `mentions[]` 里取到的那个）|

> **为什么**：飞书的 open_id 按应用隔离。A 应用看到的 B bot 是 id1，B 应用看到的自己是 id2。
> **填错 = 永不响应**（路由闸匹配不上）。

**两边各报各的才是对的**：A @ B 用的 id 与 B 自报的 id 不同 → **不是错，是视角不同**，不要"纠正"对方。

**最稳做法**：从群消息的 `mentions[]` 里取那个 id（那就是当前应用视角），**不要凭记忆写**。
**查自己是谁**：`lark-cli auth status`（看 appId）与 `fleet_roster`（看名册）。

## 七、两个必须知道的平台事实（2026-11-20 实测）

### 7.1 bot 身份默认**不能上传文件**（缺 scope）

```
lark-cli im +messages-send --file x.zip --as bot
→ 99991672 app_scope_not_applied
   缺 scope: im:resource:upload, im:resource
```

- **bot 应用要能传文件**，需在开放平台申请 `im:resource:upload` + `im:resource`
  （`https://open.feishu.cn/page/scope-apply?clientID=<app_id>&scopes=im%3Aresource%3Aupload%2Cim%3Aresource`）
- **未申请前**：文件用 user 身份上传（纯附件投递，**不 @ 任何人、不带路条**），**指令消息仍用 bot 身份**
- 下载（`+messages-resources-download`）**bot 身份即可**，不需要 upload scope

### 7.2 `ou_` open_id **跨应用视角不同**（最容易踩）

同一个 bot，在不同应用的视角下 open_id 不同：
- 群里看到的是**发送方应用视角**的 id
- 而"判断这条消息是不是 @ 我"必须用**本机 botinfo 里的 open_id**（本应用视角）

> 实测：同一台服务器 bot，别家视角 `ou_e5340…`，自家视角 `ou_a9767…`。
> **填错 = 永不响应**（对方 router 匹配不上）。

**规矩**：
- @ 别人：用**你当前应用视角**下、从群消息 `mentions[]` 里看到的那个 id
- 判"是否 @ 我"：用**你自己 botinfo 的 open_id**
- 两者不是同一个来源，**不要混用**
